01｜什麼是 RBAC？

RBAC 是 Role-Based Access Control 的縮寫，中文通常稱為「角色式存取控制」。

👤 使用者
User
→
🎭 角色
Role
→
🔐 權限
Permission
RBAC 不直接問「Andy 可以做什麼」，而是先問「Andy 是什麼角色」，再由角色決定能做什麼。

02｜為什麼需要 RBAC？

❌ 直接替每個人設定權限

每一位使用者都要逐項設定新增、修改、刪除、匯出等權限。

問題：設定重複、容易出錯、人員異動難維護。

✅ 使用角色集中管理

先建立 Admin、Teacher、Student 等角色，再把角色指派給使用者。

優點：一致、清楚、容易維護與稽核。

範例

使用者角色主要權限
AndyAdmin新增、修改、刪除、查詢、匯出
MaryTeacher查詢學生、修改成績、匯出成績
JohnStudent查詢自己的資料

03｜Authentication 與 Authorization

🪪

Authentication

身分驗證：確認「你是誰」。

例如：帳號密碼是否正確？Token 是否有效？

🛡️

Authorization

授權：確認「你能做什麼」。

例如：你是否可以刪除使用者？

🎭

RBAC

RBAC 是 Authorization 的一種實作方式。

它根據使用者擁有的角色判斷存取權限。

04｜JWT 與 RBAC 的關係

JWT 不是權限管理系統。JWT 的主要工作，是攜帶使用者的身分資訊與 Claims。

05｜ASP.NET Core 中的角色授權

只要求使用者已登入

[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile()
{
    return Ok();
}

只允許 Admin

[Authorize(Roles = "Admin")]
[HttpDelete("users/{id}")]
public IActionResult DeleteUser(int id)
{
    return NoContent();
}

允許 Admin 或 Teacher

[Authorize(Roles = "Admin,Teacher")]
[HttpGet("reports")]
public IActionResult GetReports()
{
    return Ok();
}
前端隱藏按鈕只是介面控制，真正的安全授權一定要在後端 API 執行。

07｜RBAC 的限制

角色適合處理「某一類人可以做什麼」，但不一定能處理資源關係與動態條件。

Resource-Based

使用者只能修改自己建立的文章。

Claims / Policy

只有 IT 部門且職級為 Senior 的人可以操作。

ABAC

依據部門、地區、時間、裝置等屬性共同判斷。

09｜重點整理

JWT

負責攜帶身分資訊與 Role Claim。

RBAC

負責定義角色與權限的對應關係。

Authorize

負責在 API 上執行實際的授權判斷。

Authentication 解決「你是誰」；RBAC 解決「你的角色能做什麼」。
